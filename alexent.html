断点 · 为什么通用聊天不够

ECM 迁移项目里，知识和动作之间断成了四截

迁移顾问的日常工作横跨文档库、项目表格、会议纪要和聊天工具。把通用 AI 聊天直接放进来，并不能把这些断点接上——它不知道项目走到哪一阶段，也不敢为答案负责。

断点 01

知识躺着不动

ArchiveLink、DMS 的迁移 runbook 和 SAP Note 沉在文档库里，顾问靠个人记忆和搜索经验把它们翻出来。

断点 02

状态散在多处

阶段进度、任务分配、会议结论各自存放，AI 看不到"当前事实"，给出的建议常常停留在上一个版本。

断点 03

答案不敢引用

通用聊天不带来源、不带审核状态。在部门协作里，没有证据链的 SAP 结论不敢被直接采用。

断点 04

记忆没有边界

跨项目、跨成员的对话内容如果没有作用域隔离，部门数据就有串扰和泄露的风险。

知识位置文档库 / SAP Note
⇢
传递方式顾问个人记忆
⇢
使用现场通用聊天窗口
⇢
最终结果协作里不敢直接采用

工作流 · 五阶段交付骨架

先给交付一个骨架，再让 AI 长在骨架上

工作台把 ECM 迁移拆成准备、设计、构建、测试、上线五个阶段。阶段流转由角色权限控制——项目经理确认后才推进；任务看板与会议日志挂在项目下，DOCX、XLSX 可以导入解析，也可以一键导出交付物。

阶段目标

摸清家底

确认源系统与目标系统、涉及的文档技术（ARL / GOS / DMS / BDS）与迁移范围，把项目名册和角色职责一次性定义清楚。

AI 在这里做什么

根据项目档案生成准备阶段任务清单；从会议纪要中抽取决议与待办；回答"这类技术组合通常要查哪些 Note"。

沉淀的交付物

项目档案 · 团队名册 · 准备阶段任务板 · 会议纪要解析记录

阶段目标

定方案

为每一类文档技术确定迁移策略、目标仓库映射与校验口径，形成可评审的迁移设计。

AI 在这里做什么

基于已审核的 Knowledge Pack 给出策略候选并标注出处；把设计决策写入长期记忆，后续对话自动带上这些约束。

沉淀的交付物

迁移策略草案 · 技术映射表 · 经确认的设计决策记忆

阶段目标

跑通迁移

配置迁移程序与内容仓库连接，在小样本上跑通端到端迁移链路。

AI 在这里做什么

回答具体报错与配置问题——答案附来源章节与审核状态；证据不足时明确拒绝生成 SAP 专业结论，而不是编一个看似合理的配置。

沉淀的交付物

配置检查清单 · 问题排查记录 · 样本迁移结果

阶段目标

验证口径

按设计阶段定下的校验口径核对数量、可读性与链接完整性，让业务部门签字确认。

AI 在这里做什么

把测试会议中的问题逐条抽成任务并指派；追踪每个缺陷的状态，保证测试结论可追溯。

沉淀的交付物

校验报告 · 缺陷任务列表 · 签字确认的会议结论

阶段目标

平稳切换

执行切换窗口、回退预案与上线后观察期安排，把项目交付给运维。

AI 在这里做什么

汇总整个项目的已确认决策与教训，生成上线检查单与交接摘要，导出为可归档的 DOCX / XLSX。

沉淀的交付物

上线检查单 · 交接摘要 · 项目经验记忆库

阶段推进是角色感知的：流转动作由服务端按项目角色校验，普通成员无法越权改阶段——AI 也一样，只能通过同一套受权限约束的工具来操作。

知识治理 · 让答案敢被引用

每条 RAG 答案，都带着来源、章节和审核状态

知识以 Knowledge Pack 的形式进入系统：Markdown 按章节切块存入 Chroma，frontmatter 声明负责人与审核状态。检索有距离阈值兜底，答案永远把证据摆在结论旁边。

正常回答

结论旁边永远有证据

「ARL 迁移前建议先核对内容仓库证书有效期」——来源：arl.md · 迁移前检查章节 · 状态 reviewed。顾问可以顺着标注回到原文核对。

证据不足

拒绝，也是一种正确回答

当检索不到足够相关且合规的知识时，系统明确说明"当前证据不足以给出 SAP 专业结论"，并建议补充或审核对应 Knowledge Pack——把不知道也说成产品能力。

记忆与权限 · 边界先于智能

每一次记忆都有作用域，每一次改写都有审计

协作场景里，"记住"本身是风险动作。Alexent 把状态、对话和长期记忆拆成三层，各自有明确的作用域与覆盖规则。

第 1 层

实时项目状态

阶段、任务、会议记录存放在 SQLite 专属表中。实时字段永远覆盖回忆文本——模型看到的是当前事实，不是聊天记录里的旧版本。

第 2 层

作用域对话

消息按 用户 + 项目 + 会话 精确隔离持久化。模型只拿到有界的最近窗口；会议文件解析走独立会话，文档里的隐藏文本不会污染可见对话。

第 3 层

审计长期记忆

只有经确认的决定、约束、偏好、事实与教训才进入长期记忆。重复写入返回 NONE；替换与删除产生带历史保留的 UPDATE / DELETE 审计事件。

作用域规则

项目事实共享，个人偏好私有，谁也不越界

  • 项目事实经确认后共享给有授权的项目成员，跨项目不可见。
  • 全局偏好始终用户私有，不会流进其他身份或其他项目。
  • 权限校验在服务端完成，前端隐藏入口不等于权限。
  • 记忆管理提供查询、历史回溯与删除接口，记忆不是黑盒。

Agent · 工具化而非自由发挥

LangGraph 驱动的 ReAct Agent，只能走受权限约束的工具

Agent 通过 LiteLLM 兼容端点接入模型，以 ReAct 模式调用工具。它能做的每一件事——查任务、改阶段、写记忆、检索知识——都经过与界面同一套权限与审计通道。

工具组 A

生命周期工具

读取项目档案、查询与更新任务、登记会议纪要、按角色校验后推进阶段。AI 对项目状态的所有读写都落在审计范围内。

工具组 B

知识与记忆工具

检索受治理的 Knowledge Pack，按作用域读写长期记忆。证据不足时，工具层直接返回"无合规证据"，而不是让模型硬答。

工具组 C

交付物工具

解析上传的 DOCX / XLSX（大小受限、独立会话），把检查单、交接摘要等导出为可归档文件——让对话结果变成交付物。

用户提问→ReAct 规划→工具调用（权限校验）→证据 / 状态回读→带标注的回答

判断 · 这个项目教会我的

协作 Agent 的可信度，是设计出来的

01

状态先于对话

让 AI 读写结构化的项目状态，而不是让它从聊天记录里猜。实时字段覆盖回忆文本，事实只有一个来源。

02

证据是界面的一部分

来源、章节、审核状态不该藏在日志里，而要显示在答案旁边——用户能不能核对，决定了答案能不能被用。

03

失败要有默认方向

检索阈值、状态白名单、fail-closed 生成：每个不确定的环节都要事先决定"往哪边倒"，而不是交给模型自由发挥。

这次实践让我更确信：Agent 的可信度不来自更强的模型，而来自作用域、证据链和审计——把"知道边界"本身设计成产品能力。
